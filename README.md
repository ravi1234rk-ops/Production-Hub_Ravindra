# Creative Lab

A small shared project-management and asset-audit app for a trusted local network. It combines the project schedule, team assignments, progress/time logging, and pre-audit/final-audit details from the two existing HTML tools. New workspaces start with no sample projects or production tasks; they retain the configured team roster, DPM routing matrix, and business calendar. Audit records start empty because the old auditor sent submissions to an external Google Apps Script; this app stores new records locally on the host instead.

Upgrading an existing workspace does not clear or rewrite its saved project/task records. This keeps live workspace data intact; back up the data file before any manual cleanup.

## Start the app

Requirements: Node.js 20 or newer. Install dependencies once after cloning or updating the app.

```sh
cd team-project-hub
npm install
npm start
```

Open the `localhost` address shown in the terminal on the host computer. The server also prints any available LAN addresses; teammates on the same network can open one of those addresses in a browser. Keep the host computer and app running while teammates use it, and allow the selected port through the host firewall if required.

The first person to open the app creates the global Manager account. Managers create teammate logins and assign roles and department memberships in **Team & leave › Accounts**. A Team Manager manages projects, audits, and leave only within assigned departments; Leadership has global read-only reports; Auditor and Executioner/Designer access stays scoped to their assigned department(s). The global Manager retains workspace administration and Workfront import rights. A person’s saved account profile—not a selector on the sign-in screen—controls access. Existing accounts are not assigned a department during upgrade: the Manager must review and assign each person. Use strong, unique passwords and share each password securely. Accounts are stored on the host; the first Manager account is not resettable from the app, so keep its password safe.

## What is included

### Production, audit and executioner workflows

- The empty **Projects** navigation item is hidden. Imported Workfront projects remain available in Overview, Managers and Workfront reports; local project records continue to support audit and allocation data.
- Overview Open projects and Due this week include only Current, Pre-Audit, Audit Ongoing, Execution in Progress, Awaiting Execution and In QC. Priority project cards include Current, Execution in Progress, Awaiting Execution and In QC only.
- PPT/Gslide production and QA AHT use the same matrix rows as iPDF. Named roster-member Bug Fixing is included only in that member's department; role-only/default Bug Fixing is excluded. In QC projects with open Design-member Bug Fixing carry a red **BUG** label. In Progress Engagement Lead Review tasks are not reported.
- Manager **Asset audits completed Today** counts Workfront Asset Audit tasks marked Complete using their actual completion date, not the date a local audit form was saved. Missing actual completion dates are flagged for a Workfront detail sync.
- Asset Audit includes pending CRs assigned to named Managers, Team Managers or Auditors with neither acceptance nor completion dates. Recording a CR audit never completes or changes the parent project's production stage. The form prefills Market, Primary Channel and Project Owner from Workfront Project Details, retaining the project owner when market-based backups are selected.
- **Hygiene** provides Managers, Team Managers and Auditors one process-adherence row per project with primary material, material expected date, planned completion/SLA, request type, complexity and page count. Green means match, light red mismatch, and amber doubtful; all states also have text labels. Comparison details retain QA assignment/status and CR complexity checks. The latest known auditor's full-audit boilerplate in Asset Audit task or project Updates is the first source per field; the latest passed local full audit supplies missing fields. Task descriptions without an authored Update are not trusted. Page counts must be explicitly labelled, never inferred. Only unambiguous ISO delivery dates are automatically compared; ambiguous boilerplate dates remain visible for review. Planned completion is compared with material expected delivery and the existing SLA rules. **Edit verification** records selected local outcomes with a required evidence note, verifier and timestamp; it never writes to Workfront or falsely labels a manual result source-corrected. Manual results expire when comparison values or audit evidence change. **Recheck details** invalidates manual overrides, preserving their history, and compares the latest imported snapshot; sync first for remote corrections. CSV retains one project per row and all check evidence. Date/date-range, project and undated filters apply to the report and export.
- Executioners land on **My work**, restricted to their own projects, tasks and CRs, with status, due/overdue indicators, time left to the material-date deadline, current AHT benchmark versus logged hours, and Start/Hold/Stop controls. **KPI / performance** is available as a personal read-only view, including quarter selection; the separate AHT matrix navigation remains hidden for executioners. One timer per user persists across refreshes. Hold saves elapsed time and pauses; Start resumes; Stop saves and ends without completing the task. Daily logs split elapsed time at local midnight. A timer can still be stopped after its assignment is reassigned.
- **Gantt timeline** is available to every role, including Executioners. **Log hrs** opens the hours form on the selected task: assigned executioners may log their Workfront Build, CR and Bug Fixing tasks; local open tasks are available to their assignee or a scoped manager. Existing server-side assignment and department scopes still apply.
- Each assignment has a persisted self-QC checklist. Executioners use **only the channel worksheet**: Banner 15, iPDF 44, Print 13, PPT/Gslide 25 checks (the PPT workbook's `Checklist` tab). Graphics Audit and Brand Guidelines do not appear in executioner checklists or downloads. Auditors use only the **Graphics Audit** worksheet (13 checks), also accessible from the full audit form for their assigned Asset Audit task. PPT/unsupported auditor channels use the shared Graphics Audit worksheet; its source is labelled. Executioners get one **Done checkbox** per checkpoint with optional notes. Previously saved N.A. or In Progress results and notes stay intact until the checkbox changes; they are never silently marked Done. Auditors retain result dropdowns, including N.A. with a required explanation. Every approved checkpoint must remain present. Downloads are real XLSX workbooks containing project metadata, document links and the role-appropriate checkpoint results/comments, ready for upload to Workfront. Additional checks are editable; unsupported execution channels keep an explicitly unapproved starter checklist. To update source templates, edit the workbooks and run `node scripts/import-checklists.js "/path/to/Checklists"`; the source config retains all imported tabs while runtime role selection excludes inappropriate tabs. Saved answers merge by stable checkpoint ID, without reintroducing removed worksheets as additional checks.
- QA handoff supports **Copy handoff for Workfront** with formatted HTML and plain text, plus an optional email draft. It includes project/CR, Puneet mention, source/output links, functional/style documents, observations and checklist link. **Add input file / Add output file** creates individual named HTTPS file records with remove controls, preserving previously saved links. Audited source links prefill the form. Add output and uploaded checklist URLs before sending. Self QC is Done only when all checks are Done or N.A. with an explanation. If rich clipboard access is unavailable (for example insecure LAN HTTP), the visible preview remains available for manual copy; no false copied confirmation is shown.
- **Quality / FTR** provides personal results and a Manager member matrix with CSV export. Only non-executioner QA accounts can explicitly confirm Pass or Rework with an evidence note. Completion alone never implies FTR: it requires an explicit first-time QA pass, no linked bugs and no previous recorded Rework. CR-specific bug attribution requires a CR ID; unidentified project bugs are not guessed onto a particular CR.
- Quality reporting starts **1 July 2026**, with Daily, Monday–Sunday Weekly, Monthly, Yearly, YTD, since-start and undated-evidence views and a member filter. A separate **Workfront task / CR instances** table lists all available named source assignments in the selected period, including Bug Fixing and Asset Audit, without treating tasks as deliverables. My work and quality rows link to actual Workfront task/issue IDs and parent project URLs; legacy exports without stable object IDs use the available project link rather than inventing task URLs. Local-only records cannot link to a nonexistent Workfront object. Completed projects/individual CRs use actual completion dates; multiple Build tasks do not complete a project until all are complete with verified dates. Pending evidence is bucketed by QA evidence date or entry date. Undated completed work is flagged, never assigned an invented completion date or FTR result.
- Named Bug Fixing appears in **My work**, including its own type filter, timer, checklist and **Update progress** action. Executioners and Auditors can record progress/completion evidence without adding duplicate hours. Stop the timer before recording 100%. These actions update local execution records only, not Workfront.
- **Learning & feedback** captures project-linked Learning, Challenge or Feedback entries from assigned members. Managers see/filter all entries within their scope and mark them Reviewed/Actioned with a visible response. Managers can publish a titled team best practice; Challenges require an Actioned status and solution/response first. Members see the scoped best-practice library, source project, original learning and approved response.
- **Work log** combines personal task-log totals and **Non-productive hours** (Training, Meeting and Other), retaining saved records and existing forms. Legacy Activity links open Work log. Future/pre-reporting dates and combined daily totals above 24 hours are rejected. Team utilization includes these categories for all scoped roster roles, including auditors, and distinguishes planned utilization, productive logged hours and total recorded utilization (productive + non-productive). Managers can inspect all scoped members' dated activity details in utilization and filter Work log by member/date range. Non-productive hours never increase productive effort, completed assets or FTR.
- **Audit clocks** persist actual Start / Hold / Stop sessions independently of planned execution dates. Opening a Workfront audit or CR audit starts its clock when no other audit is active; manual project forms also offer Start audit clock. Hold saves elapsed time and pauses; Stop saves and ends; saving an audit stops its matching clock. Closing a dialog does not silently stop/pause it: active clocks remain visible on the Audit page, including after reload. Only one audit/execution clock can run per person. Time is split at local midnight and included once as productive audit effort in utilization. **CR audit** is a compact complexity/start-date/notes form; metadata comes from the parent project. Low/Medium ETA is one business day, High three, excluding weekends and configured holidays. It records the CR only, never completes or allocates the parent project.
- **Hygiene › Project SLA** uses **Actual Start Date from Project Details to Planned Completion Date**, never Projected/Planned Start. It flags overdue open projects and late actual completion and exports CSV. A known planned-date breach remains flagged even when Actual Start Date is missing, with the missing evidence explicitly identified. Missing actual completion evidence is not an on-time result.

### Approved KPI review

**KPI / performance** is a scoped scorecard for Managers and a personal read-only scorecard for Auditors and Executioners. Executioners also see their current AHT benchmark versus logged hours in My work. The supplied Q2 workbook defines the approved quarterly rules, not current employee scores; no historical Q2 ratings or comments are copied into October performance.

**Log a KPI issue → Upload evidence** accepts multiple optional files: up to 10 files, 5 MB per file and 10 MB combined. Evidence is stored with the issue in the workspace database and remains available after withdrawal. Recorded issues show download links to viewers within the issue's existing role/member scope. Files are downloaded as attachments, never rendered inline; keep the required issue/evidence note to explain the files.

- **Load period** supports Monthly, Quarterly, Half-yearly and Yearly and preserves a loaded selection across background data refreshes. Concurrent loads cannot replace a newer selection with an older response; load errors retain the previous report with a visible error.
- **Monthly** reports show month-specific evidence plus **quarter-to-date scores using the approved quarterly thresholds**, not reset monthly miss thresholds. Managers can review QTD evidence through the displayed as-of date separately from the full-quarter review. **Quarterly** uses the original approved full-quarter rules.
- **Half-yearly / Yearly** scores average the latest non-recalled, final published quarterly snapshots, not raw half-year/year miss counts. Every expected quarter is required; missing, provisional or pre-1-Oct-2026 quarters leave the roll-up incomplete with scores unverified. Earlier coverage is never fabricated.
- **Publish** explicitly creates an immutable, versioned member-visible snapshot for the selected member/period, with publisher, timestamp and required publication/revision note. A closed, fully confirmed period can be final; otherwise Managers must explicitly allow a provisional publication. Correcting a report creates a new version, preserving prior snapshots. Recall requires a reason and retains the audit trail. Members and Managers can download each published version as CSV; later evidence changes do not silently modify an already published report.

- Weights: Manager feedback 20, Productivity 30, On-time Delivery 10, Quality 30, Process adherence 10.
- Confirmed productivity interpretation: completed assets versus the highest same-team, same-role peer count; ≥90% = 30, ≥85% = 24, ≥70% = 18, ≥40% = 12, below 40% = 6. Empty benchmarks remain Not verified. Auditor counts use completed Asset Audit work, deduplicated per project/CR.
- Quality: 0–2 misses/quarter = 30; 3 = 25; 4 = 15; 5+ = 0. Confirmed QA rework or published Design QA bulletin results are quality evidence; bulletin bugs automatically count as quality misses and linked-delivery FTR failures without mandatory Workfront validation. A Bug Fixing assignment alone is not a confirmed defect or fault. Missing QA is never an assumed pass. Managers can use **Verify / correct FTR / Bug** on any draft row to correct a result or exclude it with a reason; published weeks require a corrected draft and republication. Original source bug details remain preserved. Managers can validate audit-quality misses. Link issues to the same delivery to avoid double-counting its confirmed miss.
- On-time delivery: more than one miss/quarter = 0, otherwise 10. Actual task completion is compared with planned completion. Auditor delay also includes open overdue Asset Audit tasks. Missing timeline evidence requires Manager review.
- Process adherence: fewer than five validated misses = 10; five through ten = 5; over ten = 0. Missing historical compliance/checklist evidence must be reviewed, not automatically penalized.
- Manager feedback: four Met/Not met criteria, five points each (extra mile/cross-skilling, business-impact action items, mandatory training, leave/transport/office adherence). Training time alone does not prove mandatory training completion.
- Approved component 1–5 rating bands are shown alongside points. Productive utilization is informational against 150h/month (450h/full quarter); no extra unapproved utilization scoring is added. Overall 1–5 rating is explicitly chosen by the Manager; the workbook does not supply an unambiguous total-/100 conversion.
- Managers log dated, evidence-backed KPI issues visible to the affected member. Withdrawals retain the reason and audit trail. Final reviews require evidence checks, complete feedback criteria, a coverage declaration and overall rating. Changed performance evidence or issues invalidate an earlier confirmation for re-review.

### Historical evidence coverage

Current Workfront queues are not a complete archive. Source completion dates, Actual Start Date and explicit QA evidence must be supplied to validate historical buckets. Missing dates are reported as unknown rather than backfilled with import/last-update dates.

The Admin's **KPI › Import dated historical Workfront evidence** accepts a history-only XLSX Tasks, Projects or Change rounds export, without replacing active assignments. Required column names are listed in the form. Task exports need stable **Task ID** and **Actual Completion Date**; include **Entry Date** for bug-date reporting. Project exports need **Actual Start Date**, **Planned Completion Date** and **Actual Completion Date**. Only PRD WPP Production records are accepted. Imported/cached records persist when they disappear from active reports; an empty field in a later queue export does not erase known historical completion evidence. This is reporting evidence, not active queue state. QA passes require explicit evidence; they are never inferred from missing bugs.

### Quality / FTR and weekly Design QA reports

- Quality/FTR shows deliveries within the user's existing team/assignment permissions. The approved workbook import/publication workflow remains **Design only**; other teams require an explicitly confirmed QA result and first-pass evidence. Four summary cards and a concise period bulletin replace the long default lists. Member breakdown, source tasks and bug evidence are collapsed; delivery exceptions and weekly QA review use ten-row pagination. Source previews are capped at twenty rows; CSV/Excel exports retain complete data.
- FTR is **first-time-right deliveries / deliveries with an accepted first-pass decision**. Published Design QA bulletin results are accepted without a mandatory validation step; manual verification/correction is optional. Builds and CRs count once across executor/QA rows: a Build per project, an identified CR per CR number, and a bulletin CR (the bulletin carries no CR number) per QA Task ID. Bulletin deliveries by executors outside the production roster count in team and leadership FTR, are shown as bulletin only, and do not enter any member's KPI. Bulletin bug-only rows with no delivery record are not deliveries and stay outside the denominator. All accepted executor evidence must support a first-pass result; any reported bulletin bug or confirmed rework prevents FTR. Completion dates are required. Missing/unpublished QA, CRs without a CR number or bulletin QA Task ID, and a QA pass with unknown first-pass status are unverified and excluded from the denominator. No denominator is **N/A**, not 0% or 100%. Draft workbook counts remain separate until publication. Bug task presence alone does not overturn QA evidence.
- Bug evidence lists named Design Bug Fixing assignments, human-authored task Updates and executor rework requests in Project Updates. Assignment means work to perform, **not responsibility for the defect**.
- Managers/Auditors can upload the QA workbook's **Deliveries** and **Bugs** sheets or add a dated QA result manually. Imports are unpublished drafts. All-team source totals are distinguished from Design candidates, defect counts and bug rounds.
- Managers must corroborate the original delivery executor against Workfront Project Executor / Build assignment, or the individually identified CR and assignee. Workbook aliases need explicit confirmation. The Bug Assignee is never substituted for the original executor. Missing projects, original executors and individual CR IDs remain unresolved.
- Weekly review is **Match Workfront IDs → review exceptions → publish**. A Manager's single Match action approves rows whose exact Workfront project ID/reference, original executor and CR checks all pass; no per-row form is needed for these matches. Unmatched or stale rows stay in **Needs attention**, shown by default. Review can correct the Workfront ID/assignment or exclude a row with a reason. Matching alone does not publish or affect KPI. Source/defect details are collapsed, and All / Matched / Excluded views retain access to every row.
- QA matches exact project reference numbers or internal Workfront project IDs, never project names or partial IDs. The **Hygiene** link uses the resolved project reference and opens the same project's adherence/SLA checks; the Workfront ID/project filter also applies to their CSV exports. No match is treated as evidence that Hygiene checks passed.
- Publish only after every included row is validated against available source evidence; exclude unrelated rows with a reason. Published snapshots are immutable, member-visible and versioned; corrections use a new draft, and recall preserves the audit trail. Changed source evidence invalidates validation.
- Published QA drives Design Quality KPI: one miss per affected project or identified CR per responsible member, deduplicated across rows, weeks and linked Manager issues. Defects/rounds do not multiply misses. Completed Design work without published QA remains unverified, not automatically perfect; open, undelivered work does not block completed-work quality.
- Bug-only records missing from Deliveries do not become completed work or FTR. The supplied 12-18 October workbook has 226 all-team deliveries, 55 bug rows and 8 unmatched bug rows. Its 41 affected delivery rows imply 81.86% reported FTR, not the bulletin's 78%; these figures are not forced to reconcile or used as Design KPI.
- Hygiene reads explicit labelled fields from a known auditor/Manager's audit result in Asset Audit task / project Updates, with author/date provenance and passed local audit fallback. Workfront Comments reads report loaded/partial/unavailable coverage explicitly; an expired Workfront login must be renewed in Workfront Reports before live evidence can be verified. Blank first-round/QC scores are never interpreted as FTR.

### Automatic Outlook email for KPI issues

In **Team -> Team members**, an Admin can edit the **WPP Production email** field for every member, including all Managers and Team Managers. Use a single `@wppproduction.com` address per person; duplicate addresses are rejected. Clearing the field disables that person's notifications.

When a Manager or Team Manager logs a **new KPI issue**, the server sends the issue date, category, project/delivery reference, note, logging manager and all uploaded evidence files to the affected member. The sender is **that logged-in manager's saved mailbox**, not a shared or hard-coded sender. For Ravindra Kumar, save `ravindra.kumar@wppproduction.com` on the correct roster entry. Other managers use their own addresses. Missing mappings never fall back to another mailbox. The existing manager/team access rules and Admin-only roster editing remain unchanged.

Automatic Outlook sending uses Microsoft Graph; it does not require the desktop Outlook application. IT must provision a Microsoft Entra application with administrator-consented **application** permissions `Mail.Send` and `Mail.ReadWrite` (drafts and large attachments), and authorize the relevant manager mailboxes. Restrict its mailbox access using the organization's Exchange application access controls. Provide the three values using **either** method:

1. **Local credentials file (recommended):** copy `config/outlook.local.example.json` to `config/outlook.local.json` (excluded from Git), replace the three placeholders with the values from IT, and restrict it with `chmod 600 config/outlook.local.json`. The file is read on every send, so no restart is needed. A file readable by other users or invalid JSON is refused with a clear status message. Use `OUTLOOK_CREDENTIALS_FILE` to choose another path.
2. **Environment variables:** set `OUTLOOK_TENANT_ID`, `OUTLOOK_CLIENT_ID` and `OUTLOOK_CLIENT_SECRET` before `npm start`. These take precedence over the file.

Do not put real secrets in source control or chat. There is no global sender override: the approved application must be permitted to send from **each** configured manager mailbox.

- New issues are persisted before attempting mail; mail failures never discard KPI evidence. The issue response, toast and **Outlook notification** column explicitly distinguish missing addresses, missing configuration, failures and Microsoft acceptance. Acceptance is not confirmed delivery.
- Evidence retains the upload limits (10 files, 5 MB each, 10 MB combined). Small files use Graph attachments; files at least 3 MB use sequential Outlook upload-session chunks. Sending occurs only after every attachment succeeds.
- This is one send attempt for a newly created issue, not a bulk historical notification. Refreshes, edits, withdrawals and restarts do not resend. There are no automatic retries: if Microsoft rejects a request, the connection times out, or the server stops during sending, check the sender's **Sent Items and Drafts** before sending manually. A failed attachment operation can leave an unsent draft; Microsoft/network uncertainty must never be treated as delivery.
- Tests use mocked Microsoft responses and isolated workspaces; they never send live mail. Existing leadership/capacity copy/export features still do not send automatically.

### Automatic leadership bulletins

Open **Manager reports → Leadership production report**, or **Quality → Last week's FTR bulletin**. Managers, Team Managers and Leadership can read the prepared reports within their existing access. Executioners/Auditors keep their scoped Quality view; the last-week action switches their own period without exposing leadership reports.

- Managers default to an existing assigned team and share one selected team per report. Team Managers can select only their assigned teams; global Managers and Leadership retain an explicit all-team summary. Switching daily/weekly reports preserves the selected team. The sharing header identifies the signed-in sender without changing the saved review owner.
- Eight concise number cards show completed production, productive effort/capacity, utilisation, non-production hours, FTR, SLA, benchmark/actual and follow-up. Team breakdown, evidence and reporting rules are collapsed. **Copy email bulletin** copies the same inline-styled cards for Outlook/Gmail, with plain text as an alternative; PDF stays concise, while Excel retains full evidence.

- At **09:00 Asia/Kolkata every day**, prepare the previous calendar day's **Daily production & effort** report. On **Mondays at 09:00**, also prepare the previous **Monday–Sunday utilisation, performance & FTR** report.
- The server checks every minute and catches up the latest due daily/week periods at startup (not every missed historical period). It must be running for on-time preparation; nothing is automatically emailed. Reporting starts 1 July 2026, with the first week explicitly partial.
- Each snapshot contains separate team bulletins and a leadership summary. Capacity counts each rostered executioner/auditor once, excluding weekends, holidays and approved full/half-day leave. Multi-team members stay in a **Shared capacity** pool, never split arbitrarily. Team utilisation uses dedicated-team members' effort on that team's work divided by dedicated capacity; cross-team/shared work remains visible in effort. Global utilisation uses all dated productive effort / unique roster capacity. Shared/unmapped team utilisation is N/A. Scoped team totals exclude other teams and shared pools and are not presented as studio totals.
- Training, Meeting and Other hours are separate from productive effort. Daily effort uses saved dated work/audit logs, never distributes cumulative Workfront Actual Hours across dates, and deduplicates log IDs. Missing logs do not prove no work. Task completions and completed Build/identified-CR deliveries are separate measures. Missing completion dates are explicitly counted as unbucketed archive evidence, not assigned to a reporting day.
- Operational performance includes completed deliveries, SLA on-time/late/unknown, verified FTR, and benchmark versus actual effort for completed deliveries with both values available. Actual paired effort includes all saved dated effort through period end; it is not confused with this period's effort. Imported per-asset benchmarks are not multiplied by duplicate tasks. No new employee rating or formal KPI score is invented. Current roster/assignments are not historical headcount evidence.
- Reports start as **Draft — review before sharing** with prepared time, source sync freshness, QA coverage and missing-data caveats. Managers/Team Managers can mark their permitted team scopes reviewed with a required note; Leadership is read-only. A Manager can prepare a corrected version for late logs/QA; prior snapshots and reviews persist in the audit history, and the new version requires review again. Existing snapshots are never silently changed by subsequent imports.
- **Excel** contains Summary, Production, Effort, People and Read me worksheets. **Copy email bulletin** provides the same scoped metrics; clipboard failures expose the text for manual copying. **Print / Save as PDF** prints the selected report only. Exports retain Draft/Reviewed and source coverage labels. Preparing, reviewing or copying never sends mail.

Focused checks: `node --test test/leadership-reports.test.js test/leadership-workflow.test.js test/workflow-reports.test.js test/qa-reports.test.js`. These use isolated data and verify India-time boundaries, FTR eligibility/deduplication, shared capacity/leave, report scopes/version persistence and browser Excel/email/PDF workflows.

### Existing workspace features

- Shared project records with assignment, type, request priority, page count, complexity, progress, status, turnaround date, due date, and notes.
- Project search, status and assignee filters, AHT-based effort estimates, CSV export, an overview of upcoming work, and a Gantt timeline that can be grouped by resource or project.
- Summary, workflow-status, workload, and department cards drill through to the relevant scoped project, audit, leave, Workfront, task, or utilization records. The resulting view shows a clear filter notice with a one-click reset; cards support keyboard activation.
- Daily work logs with hours, phase, notes, and progress updates; logging 100% progress completes the project. The Gantt compares planned effort with logged hours and progress, and marks completed assignments with a green check.
- Pre-audit and audit records with the original channel / request / complexity TAT matrix, holiday-aware ETA calculation, source-file status, DPM routing, observations, dependencies, requirements, multiple input-document links, and priority. Workfront Pre-Audit items have a 24-hour hold target; Audit Ongoing items have a 4-hour target, both measured from Workfront Last Update Date and highlighted when overdue.
- Separate Pre-Audit and final-Audit email-template generation with DPM greeting, leave/backup handling, requirements and source-file formatting, and copy-to-clipboard for pasting into email. Audit data is saved locally rather than sent to the retired external sheet integration.
- A separate Market / DPM backup matrix seeded with the original 74 market assignments. Update primary and backup DPMs and the holiday calendar from the matrix window.
- Department access is enforced by the server for project snapshots and project/task/audit/Workfront operations. Email Team covers Email, Campaign, Landing Page, and eDetailer; Design Team covers iPDF, Print, PPT/Gslide, Banner, Illustration, Poster, Social Media Post, and Outbound WhatsApp; Web Team covers Website and Banner HTML; Video Team covers Video, GIF, Banner-GIF, and Banner-Animated; QA membership can view work across production departments. Campaign assets always route to Email Team. A project without a known department remains available for Manager triage; classify it before allocating production work. Designer allocation suggestions include only eligible executioners in the project department or QA.
- Final audit passes open a task-allocation window with AHT effort estimates and resource-bandwidth suggestions. Managers, Team Managers, and Auditors can also assign other project work from the project list within their scope. Updating an allocation due date leaves the existing project TAT date unchanged.
- Unified Build, CR, and Bug Fixing tasks appear in the same schedule. Fresh projects create Build tasks; Managers, Auditors, and Executioners can add CR or Bug Fixing tasks, with Executioners restricted to their own assignments. Tasks capture project, category, CR/build scope, complexity, units, priority, designer, planned start date/time, and ETA.
- Task effort uses supplied production and QA AHT rather than a fixed QA percentage. The timeline fills production effort in blue and QA effort in yellow in proportion to their estimated hours; the separate green strip shows progress. Missing AHT is labelled unavailable and is not replaced by Workfront template planned hours. Local tasks highlight overdue or capacity-expedited ETAs against their workload-based capacity date. Local CRs also retain their separate contractual ETA: Low and Medium are one business day, High is three business days, with weekends and configured holidays skipped.
- Manager, Team Manager, and Auditor task allocation suggestions include each eligible designer's remaining workload and earliest capacity date. Priority order, assignee, start date/time, and optional faster ETA overrides are editable; dragging a task in the Gantt moves its date/time or reassigns it.
- The task Gantt can be viewed by hour, day, week, or month. The **Team** filter works with resource-wise, project-wise, and task-wise grouping for both sources. Workfront task-wise grouping uses the reported task name; local task-wise grouping uses Build, CR, or Bug Fixing. In **Team & leave › Team**, Managers can select **11:30 AM–8:30 PM** per designer; new members use this shift. Existing shifts remain unchanged until selected, with the older 12:30 PM–9:30 PM and 11:30 AM–9:30 PM options retained. Changing a shift automatically reflows unstarted local assignments and their parent Build schedule, using that member's start/end times and retaining the eight-hour daily capacity. Completed tasks and imported Workfront dates remain unchanged. Workfront's hourly scale covers 11:30 AM–8:30 PM; the local scale extends to 9:30 PM when displayed tasks still use an older shift. Drag local tasks to move or reassign them.
- Gantt's **Source** selector defaults to **All production** for roles with Workfront access. Workfront Build, CR, Bug Fixing and QA (for example QA Audit) rows remain within the signed-in user's existing access scope. Named resource groups show only configured **Team** roster members. Non-roster, role-only and unassigned work is retained in **Other / Unassigned** at the bottom in every grouping and source, with original assignments visible in each row. Combined legacy labels are not split by guessing names. The **Team** filter uses roster membership for assigned work; work without a roster member uses its task/project production team. **Unassigned team** also includes non-roster assignments. Tasks completed on or before the selected **Start date** are hidden (the notice shows how many), while open work and work completing later stays visible. ### SQLite storage and migration

Stop the app before upgrading or migrating, then run:

```sh
npm install
npm run data:migrate
npm start
```

The migration imports **all** existing workspace data from `data/team-project-hub.json`, including accounts/password hashes, Workfront snapshots, reporting history, audits and configuration. It verifies an exact round trip and SQLite integrity, leaving the original JSON untouched as a pre-migration backup. Startup also imports the JSON automatically if the database has not yet been initialized. An existing SQLite workspace always takes precedence; subsequent JSON edits are not imported. Invalid JSON, invalid workspace structure or database errors stop startup rather than replacing data with an empty workspace. New installations with no JSON start with the normal account setup.

SQLite uses transactional, changed-record writes with WAL journaling. Each Workfront detail batch saves only changed records instead of rewriting the full JSON file, including the reporting history. Scraping still reads all configured report/detail pages on every run: no TTL cache hides Workfront changes. SQLite reduces storage I/O; Workfront page loading, SSO and DOM extraction still determine much of the total scrape time. Existing sync timing, error reporting, exports and role permissions are unchanged.

The database stores object structure and settings in `workspace_nodes` and ordered array records in `workspace_records`; record payloads retain every original JSON field. Nested history collections are stored separately as well. For example, SQLite JSON functions can query task statuses:

```sql
SELECT json_extract(payload, '$.workfrontId') AS workfront_id,
       json_extract(payload, '$.taskStatus') AS task_status
FROM workspace_records
WHERE node_path = '["workfrontTasks"]'
ORDER BY position;
```

Use one app process per workspace database. Keep the active SQLite database on a local disk, not a network share or a folder being actively synchronized by OneDrive/Dropbox. Set `SQLITE_FILE` to a local, non-synced location if the project is in cloud storage. For a full backup, stop the app and copy the `.sqlite` file **and any remaining matching `-wal`/`-shm` files** together; never copy just the database while the app is writing. The database and legacy JSON contain password hashes and private workspace data, so protect backups accordingly. Do not restore the old JSON over a database containing newer updates.

## Network and security notes

The default server binds to all network interfaces so teammates can connect. Use it only on a trusted, access-controlled network. Plain HTTP does not encrypt passwords or project data in transit. For any network that is not fully trusted, configure HTTPS using a certificate and key:

```sh
TLS_CERT_FILE=/path/to/certificate.pem TLS_KEY_FILE=/path/to/private-key.pem npm start
```

Do not expose the service directly to the public internet. Accounts use salted password hashes, sessions are held in memory and sent in HTTP-only same-site cookies, and only Managers can create accounts or download the JSON backup. Role checks are enforced by the server; hiding a page control is not the security boundary.

The listening host and port can be configured with `HOST` and `PORT`. `DATA_FILE` selects the legacy JSON import source; by default its `.json` extension is replaced with `.sqlite` for the database path. `SQLITE_FILE` overrides the active database location. Use the same environment variables for `npm run data:migrate` and `npm start`.

Auditors are read-only and see their own named rows, subject to project department access when mapped. Team managers see permitted projects (or known auditor-team membership for historical projects absent from sync). Unmapped/unassigned rows are manager-only. Leadership and executioner accounts have no access.

Allowed reason categories are exactly: `Actual Miss Confirmed`, `High Workload / Competing Priorities`, `Complex Asset / Additional Review Required`, `Rework / Repeat Review`, `Unplanned Operational Support / Ad hoc Activities`, `Translation/Other Project Dependency`, and `Needs confirmation`. Verification statuses are `Verified`, `Inferred`, and `Needs confirmation`. Evidence sources are `Project Updates`, `Issue`, `System activity`, and `Source workbook`. `Verified` requires evidence; `Actual Miss Confirmed` additionally requires a reviewed non-workbook source and is **never automatically assigned**. Imported descriptions remain externally reviewed assessments, not automatic conclusions.

Imports enforce matching creation month, real dates, unique case-insensitive project IDs, finite nonnegative numeric metrics (maximum 1,000,000; counts are integers), HTTPS Workfront links or empty strings, bounded text/evidence, 1–5,000 rows, at most 50 evidence items per project / 20,000 per report, and an 8 MiB JSON evidence limit. Preserve missing names/URLs/clarification fields as empty strings. No delay calculation, holiday adjustment, or hold-time deduction is silently applied.

Authenticated, same-origin session endpoints:

- `GET /api/process-audit-reports`: role-scoped month metadata and category/status choices.
- `POST /api/process-audit-reports`: `{ "report": { ... }, "replaceExisting": true }`; manager/team-manager only. An existing month without explicit `replaceExisting: true` returns 409. Imports use the existing Origin/HTTP-only SameSite session protections.
- `GET /api/process-audit-reports/YYYY-MM`: role-scoped report; optional `search`, `category`, `status` query filters.
- `GET /api/process-audit-reports/YYYY-MM/xlsx`: genuine XLSX download with the same role scope and filters. Filename: `process-audit-YYYY-MM.xlsx`.
- `GET /api/data` includes lightweight, role-scoped `processAuditMonths` metadata, not all monthly evidence.

The XLSX has **Hygiene**, **Evidence**, and **Summary** worksheets, with bold colored headers, frozen first rows, wrapped top-aligned cells, and practical column widths (wider reason/evidence columns). Hygiene retains the original eight headers in order: `Project ID`, `Project Creation Date`, `Asset Audit Completion Date`, `Production Manager Name`, `Asset Auditor Name`, `Hold Time`, `Working Hrs Difference`, `Reason for Delay`, followed by category/status/context columns. Hold Time remains an unchanged numeric source value: the source workbook does not specify its unit. Numeric metrics remain Excel numbers. Summary documents source coverage, verification definitions, and workload/timing limitations. Source-wide coverage/file information is redacted for non-managers. All imported text is written as explicit Excel strings, never formulas. Counts in the UI and XLSX are scoped to authorized rows; same-day workload counts remain source-report context, not proof of cause. Search covers IDs, people, reasons, evidence, clarification and translation requests. Download respects the active category/status/search filters.
